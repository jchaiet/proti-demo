# CI and Branch Protection

This guide documents the recommended GitHub CI and branch-protection setup for Proti.

## Purpose

The CI workflow acts as an automated quality gate for pull requests before code is merged into `main`.

The workflow also runs again after a merge to verify the resulting `main` branch.

## CI Triggers

The workflow is configured to run on:

```yaml
on:
  pull_request:
  push:
    branches:
      - main
```

This means CI runs:

1. When a pull request is opened or updated.
2. When code is pushed or merged into `main`.

## CI Jobs

### Studio

Validates the Sanity Studio package.

Checks include:

```text
Install dependencies
Run Studio tests
Build Studio
```

### Web

Validates the Next.js application.

Checks include:

```text
Install dependencies
Run Vitest test suite
Generate Next.js route types
Run TypeScript type checking
Run ESLint
Build the production application
```

The type-check step must generate Next.js types first:

```bash
pnpm exec next typegen && pnpm exec tsc --noEmit
```

This is important because types such as `LayoutProps` are generated by Next.js and may already exist locally from previous builds while being absent on a clean CI runner.

### Playwright Smoke

Runs real-browser smoke tests against a production build.

The smoke suite verifies that the application's important routes and browser behavior continue to work.

Current browser coverage includes Chromium and Firefox.

### Playwright Visual

Runs visual regression tests against the approved Chromium screenshots.

Visual coverage uses:

```text
chromium-desktop
chromium-mobile
```

Firefox is used for functional smoke coverage but does not maintain a separate visual baseline.

During initial calibration, the visual job may be configured with:

```yaml
continue-on-error: true
```

This allows screenshot differences to be inspected without blocking the entire CI workflow.

Once GitHub-hosted runner screenshots have proven stable, remove `continue-on-error: true` and make the visual job a required check.

## Runtime Versions

The current CI baseline is:

```text
Node: 24.19.0
pnpm: 10.34.1
```

The Node version should stay aligned with local development.

A root `.nvmrc` is recommended:

```text
24.19.0
```

## pnpm Cache

Because Proti uses a root workspace lockfile, CI should use:

```yaml
cache: pnpm
cache-dependency-path: pnpm-lock.yaml
```

Do not point the cache at `web/pnpm-lock.yaml` or `studio/pnpm-lock.yaml` unless those files actually exist.

A message such as:

```text
pnpm cache is not found
```

is normal on the first CI run. It means there was no previously stored cache yet.

## Local Mino Package

The Web package currently consumes Mino from a local tarball:

```text
web/mino-ui-0.0.2.tgz
```

When that tarball changes, its checksum in `pnpm-lock.yaml` must also be updated.

After intentionally rebuilding or replacing the tarball, run from the repository root:

```bash
pnpm install --update-checksums
```

Then verify the strict CI behavior locally:

```bash
pnpm install --frozen-lockfile
```

Commit the updated tarball and lockfile together.

## GitHub Branch Ruleset

Create a ruleset for `main` in:

```text
Repository
→ Settings
→ Rules
→ Rulesets
→ New ruleset
→ New branch ruleset
```

Recommended ruleset name:

```text
Protect main
```

Set the enforcement status to:

```text
Active
```

Target:

```text
main
```

or the repository's default branch.

## Recommended Rules

Enable:

```text
Require a pull request before merging
Require status checks to pass before merging
Require conversation resolution before merging
```

Recommended initially:

```text
Require branch to be up to date before merging: OFF
Require signed commits: OFF
Require merge queue: OFF
```

Force pushes and deletion of `main` should remain disabled.

## Required Status Checks

Require these checks before merging:

```text
Studio
Web
Playwright smoke
```

While visual regression is still in calibration mode, do not make it required.

After repeated stable visual runs, make this required as well:

```text
Playwright visual
```

## Pull Request Flow

The expected development flow is:

```text
Feature branch
      ↓
Open pull request
      ↓
CI runs
      ↓
Studio
Web
Playwright smoke
Playwright visual
      ↓
Required checks pass
      ↓
Review conversations resolved
      ↓
Merge to main
      ↓
CI runs again on main
```

If a required check fails, GitHub should block the merge until the problem is fixed and the check passes on a newer commit.

## Example

Create a feature branch:

```bash
git checkout -b feature/example-change
```

Make and commit changes:

```bash
git add .
git commit -m "Update example feature"
git push -u origin feature/example-change
```

Open a pull request targeting `main`.

GitHub should automatically start CI.

While required checks are running, the PR remains blocked.

Once the required checks pass, the PR becomes eligible to merge.

## Visual Regression Workflow

For intentional visual changes, do not immediately overwrite screenshots.

Run:

```bash
cd web
pnpm build
pnpm start
pnpm test:e2e:visual
```

Inspect the diff first.

If the change is intentional:

```bash
pnpm test:e2e:update
pnpm test:e2e:visual
```

Review the new screenshots and commit the approved baselines with the code change.

Do not update baselines only to make CI green.

## Suggested Verification

After creating the ruleset, test it with a small non-functional change such as a README update.

Confirm that:

```text
Studio
Web
Playwright smoke
```

appear as required checks and that GitHub prevents merging until they pass.

Once confirmed, the CI workflow and `main` branch ruleset together provide Proti's automated pre-merge quality gate.
