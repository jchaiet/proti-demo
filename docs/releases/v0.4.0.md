# Proti v0.4.0 — Release notes

**Status:** Release candidate / documentation prepared. Tagging and publishing the GitHub release remain separate steps; these notes do not imply that `v0.4.0` has already been tagged.

**Theme:** Make Proti a safely repeatable starter for **independent projects**, from clean clone and content seeding through Studio/Vercel deployment, CI, and production Presentation/revalidation.

## Highlights

### Independent initialization with Git safeguards

- Added explicit `pnpm proti:init --new-project` for a **clean starter clone** with typed `RESET GIT HISTORY` confirmation. This creates fresh independent Git history and preserves the former clone `.git` metadata in a sibling backup directory.
- Ordinary `proti:init` never silently detaches an existing repository; established projects retain history, remotes, credentials, and screenshots.
- Maintained source checkouts are protected with the local-only `git config --local proti.sourceRepository true` marker. Both initializer modes refuse to modify the marked source repository; `proti:check` recognizes its intentional `proti-demo` remote.
- First initialization adds `localhost` to Site domains for local routing and GitHub Actions, without overriding later intentional domain edits.

### Independent Sanity content and project configuration

- `proti:seed` creates/reuses the configured Site; `--starter-content` adds minimal default-locale Home, Header, Footer, and Navigation without overwriting authored content.
- Generated `proti.config.json`, local Web/Studio env files, and root/Web/Studio package identities make per-project configuration repeatable.
- The Site canonical hostname must be among Site domains; local/CI and production routing require matching **published** Site settings.

### Correct development/production Presentation

- Studio preview URL moved to mode-specific `studio/.env.development` and `.env.production` files. These **non-secret public URL files** can be committed while `.env.local` and tokens remain ignored.
- `pnpm proti:configure:production --url=https://…` updates the production Presentation URL and project config after the actual Web hostname is known, leaving development settings untouched. Redeploy Studio to apply it.
- `studio/sanity.cli.ts` takes project/dataset/optional App ID from environment variables instead of hardcoded demo IDs.

### Visual baseline lifecycle and CI stability

- First independent initialization clears inherited demo PNG screenshot baselines. `pnpm proti:visual:init` builds Web, captures project-specific Chromium desktop/mobile screenshots on a production Next server, and verifies both baseline files; `--force` is required to replace existing snapshots.
- Playwright server readiness uses `/api/health` while browser tests still verify published Sanity-backed routes.
- CI uses consistent `localhost:3000` host and `next start -p 3000`, prevents stale-server reuse, and blocks PR merges on smoke/visual failures.
- Studio setup tests isolate external CI environment variables. No hardcoded CI `SANITY_STUDIO_PREVIEW_URL` should override the production Studio file.

### Acceptance testing and diagnostics

- Added `pnpm test:proti:integration` using a disposable project and mock Sanity API. It tests setup, seeding, configuration, Git independence, screenshot lifecycle, and reinitialization without real provider changes.
- Expanded `pnpm proti:check` coverage for source-repository recognition, local/production Studio URL consistency, tracked Studio mode files, visual baselines, missing localhost routing, and published Site configuration.

## Independent-project deployment verified

During the v0.4 development cycle, a separate generated implementation was configured with its own Sanity project, Studio deployment, GitHub repository, and Vercel Web deployment. Production Presentation, draft-only preview, publish/revalidation, and GitHub Actions were tested successfully. Individual implementations still need **their own** Sanity tokens, allowed origins, webhook, and deployment environment settings.

## Initialization and upgrade guidance

**Original maintained Proti repository:** Set `git config --local proti.sourceRepository true` in each maintained checkout; **do not run `proti:init`** there.

**New website:** Clone into a separate clean directory, run `pnpm proti:init --new-project`, type the confirmation, configure secrets, seed, generate project-owned screenshots, and deploy. See [Getting Started](../GETTING_STARTED.md) and [Project Initialization](../PROJECT_INITIALIZATION.md).

**Existing independent project:** Keep the existing Git history. Do not use `--new-project` as an upgrade command. Review new scripts and Studio mode-specific URL files, remove legacy preview overrides, update/check `proti.config.json`, and rerun `pnpm test:proti` plus application tests.

**Version alignment:** Verify root/Web/Studio package versions are `0.4.0`, align Web's `next`/`eslint-config-next` versions, and regenerate/check the pnpm lockfile before tagging. Mino UI is independently versioned.

## Known limitations / planned follow-up

- v0.4 visual screenshots still represent **published Sanity content**; editorial text/navigation changes can cause meaningful screenshot diffs unrelated to CSS. Proposed **v0.5.0** work is a deterministic fixture-driven visual harness covering representative pages/components and interactive states. A dedicated regression Sanity dataset is optional for deeper CMS integration, not a prerequisite for current screenshots.
- The initializer doesn't provision Sanity projects/tokens, Vercel projects, GitHub repositories/secrets/rulesets, webhooks, or author translated content. These require external provider setup.
- Current acceptance tests use mock provider endpoints and do not replace a real deployment check for a new project.
